Climate Explorer — Method Notes

What this tool computes, which published method each quantity implements, and — the part that matters most when you cite it — what each number actually describes. The arithmetic here is not a rule of thumb: it is an implementation of somebody's published method, which raises the standard for provenance and for the scope of any claim made from it. Everything below is read from the source code. Where the code makes something unclear, or names no source at all, this page says so rather than inferring.

Three things to know before you cite a number

  1. The comfort figures describe outdoor air, and there are two of them. The psychrometric chart plots the weather file's own hours against the ANSI/ASHRAE Standard 55 still-air zones (“ASHRAE 55” hereafter, which is the code’s own term). The Comfortable hours tile is therefore the share of outdoor hours a person standing outside in still air would find comfortable — no building, fabric, gain, system or control enters it. It counts an hour that falls inside either zone: winter 19.5–24.5 °C or summer 22.5–27.5 °C, both bounded by humidity ratio 0.004–0.012 kg/kg. The zones overlap over 22.5–24.5 °C and an hour there is counted once. A second tile, Outside comfort band, is a different quantity computed a different way: dry bulb alone against the two sliders you set, default 20 and 26 °C, with humidity ignored. Say which one you are quoting.
  2. There is no adaptive comfort in this tool, although the code contains it. The ASHRAE 55 adaptive band is implemented — neutral temperature 0.31 × prevailing + 17.8, with the ±3.5 K and ±2.5 K acceptability limits — and no view calls it. There is no control for it and no chart draws it, so nothing a reader can do in the interface will produce an adaptive result. Every comfort figure this tool reports is the static, still-air zone. For a naturally ventilated building in a warm climate that understates comfort, and the tool cannot be cited for adaptive comfort at all.
  3. A wind frequency means nothing without its binning. This tool offers 8, 12, 16 or 36 direction sectors — 16 by default, centred on north — and bins speed into fixed bands at 0.5, 2, 4, 6, 8, 10 m/s. Hours below 0.5 m/s are counted as calm and held out of the direction bins entirely. Change the sector count and every percentage on the rose changes, because the same hours are divided among a different number of bins. Two roses drawn from the identical weather file will disagree if they were binned differently, so a quoted frequency must name the tool, the sector count and the speed bands — and before setting this rose beside one from another application, check that application's own binning first.

What is read, and what is derived

Twenty-five meteorological quantities are read straight from the file, along with the year, month, day and hour of each record. Five more are computed on load and behave in every other respect like file data:

derived on load solarAltitude solarAzimuth humidityRatio enthalpy wetBulb

Note which quantity is not in that list. Dew point is read from the file, column 7, not recomputed from humidity — so the dew point you see is the file author's value, and it need not be perfectly consistent with the humidity ratio the app derives from dry bulb and relative humidity. A psychrometric dew-point inversion exists in the code and is not used for the loaded series.

Both derivations are eager rather than lazy, and the source gives the reason plainly: "Computed once on load so view switching stays instant." The cost is a few hundred milliseconds at import; the benefit is that changing view, variable or period never waits on a recomputation of 8,760 solar positions.

Station pressure is recorded hourly in an EPW, but not always. Where it is missing the app substitutes a pressure derived from the site elevation, which comes from the LOCATION header. If the header omits elevation, it is taken as 0 m, which is sea level and not a flag — a file with no elevation silently gets sea-level pressure.

Psychrometrics

Temperatures in °C, pressures in Pa, humidity ratio in kg water per kg dry air, enthalpy in kJ per kg dry air. Three of the four relations carry an ASHRAE equation number in the source; the fourth group does not.

standard pressure at altitude z ASHRAE eq. 3 p = 101325 × (1 − 2.25577e−5 · z) ^ 5.2559 saturation vapour pressure, T in kelvin ASHRAE eq. 5 and 6 over ice (t < 0 °C) ln p_ws = −5674.5359/T + 6.3925247 − 0.009677843·T + 6.2215701e−7·T² + 2.0747825e−9·T³ − 9.484024e−13·T⁴ + 4.1635019·ln T over water (t ≥ 0 °C) ln p_ws = −5800.2206/T + 1.3914993 − 0.048640239·T + 4.1764768e−5·T² − 1.4452093e−8·T³ + 6.5459673·ln T the code cites no equation number for these three W = 0.621945 · p_w / (p − p_w) h = 1.006·t + W·(2501 + 1.86·t) RH from W by inverting the first of those

Wet bulb has no closed form, and the code does not pretend otherwise. It solves the adiabatic-saturation relation numerically:

wet bulb, by bisection ASHRAE eq. 33 / 35 t_wb ≥ 0 W* = ((2501 − 2.326·t_wb)·W_s − 1.006·(t − t_wb)) / (2501 + 1.86·t − 4.186·t_wb) t_wb < 0 W* = ((2830 − 0.24·t_wb)·W_s − 1.006·(t − t_wb)) / (2830 + 1.86·t − 2.1·t_wb) bracket lo = min(dew point, dry bulb), hi = dry bulb stopping 60 halvings, fixed

Both bisections in the module — wet bulb, and the dew-point inversion bracketed at −100 to +100 °C — run a fixed 60 halvings with no tolerance test and no convergence check. There is no early exit and no failure return. Sixty halvings of a 100 K bracket is far below any precision the data justifies, so this is not a limitation in practice; it is worth stating exactly because "converged to a tolerance" would be the wrong description of what happens.

Comfort

Two zones, drawn as rectangles on the psychrometric plane. Their sides are the comfort temperature limits and their top and bottom edges follow constant humidity ratio:

ZoneDry bulbHumidity ratio
Comfort — winter (1.0 clo)19.5 – 24.5 °C0.004 – 0.012 kg/kg
Comfort — summer (0.5 clo)22.5 – 27.5 °C0.004 – 0.012 kg/kg
 The 0.012 kg/kg upper limit is the conventional one and is a settable value in the state, though no control exposes it. The clo values appear in the zone labels and nowhere else — no clothing value enters any calculation.

These zone limits are fixed in the source. The comfort sliders in the toolbar do not move them. Those sliders drive the band drawn on the time series and the Outside comfort band tile, and nothing else.

The adaptive band is implemented and unreachable, as the opening notice says. For the record, since the code contains it and a reader may find it:

ASHRAE 55 adaptive band — implemented, never called neutral = 0.31 · prevailing + 17.8 80% acceptability neutral ± 3.5 K 90% acceptability neutral ± 2.5 K prevailing is clamped to 10 – 33.5 °C before use, and a validity flag is returned alongside — which nothing reads prevailing mean outdoor temperature exponentially weighted running mean of daily means, α = 0.8 — but the Standard permits 0.6 to 0.9 and fixes no value

The clamp is the behaviour to understand if this is ever wired up: a climate outside the standard's 10–33.5 °C validity range does not get a refusal, it gets a band computed from the clamped value. The function does return a flag saying so. No caller reads it. One further detail worth knowing before trusting the running mean: it is seeded from the last seven daily means in the array — the end of December — not from the week preceding the period being evaluated.

A provenance limitation worth recording while the code is open. The code attributes α = 0.8 to ASHRAE 55, and the Standard does not fix that value — it permits the running mean with α between 0.6 and 0.9. The figure is the EN 16798-1 default, which the code does not name. The implementation is defensible; the attribution is loose. Do not cite Standard 55 as the authority for 0.8 itself.

The passive-strategy polygons

The source names its lineage directly: the polygons "follow the Givoni–Milne bioclimatic construction used by Ladybug and Climate Consultant: they show which hours a strategy could bring into comfort." There are three, not the full Givoni set:

StrategyExtentWhat the polygon asserts
Natural ventilation22.5 → 32 °CComfort extends to a higher temperature when air moves, within the same humidity band.
Evaporative cooling27.5 → 45 °CAny state at or below the 21 °C wet-bulb line can be driven into comfort by adding moisture. Built by sweeping that constant-wet-bulb line in 1 K steps.
Internal heat gain12.5 → 19.5 °CCool but dry hours that a building's own occupants, lights and equipment could lift into comfort.
 No passive-solar polygon, no dehumidification, no humidification, no conventional heating or cooling region. A student who has met the full Givoni chart elsewhere will find four of its regions missing here.

Two counting details that change what the legend percentages mean. First, each polygon is counted independently, so the strategy percentages overlap and will sum to more than 100 — they are not a partition of the year. Second, the polygons are clipped to the saturation curve when drawn but not when counted, so a polygon whose corner sits above the saturation line contributes an area to the count that the chart does not show and that no real air state could occupy.

Solar position

Following the NOAA General Solar Position Calculations. Angles are degrees at the module boundary and radians inside; azimuth is measured clockwise from true north; times are local standard time with no daylight-saving shift, matching the EnergyPlus convention.

γ = 2π/365 · (doy − 1 + (hour − 12)/24) fractional year E_t = 229.18 · (0.000075 + 0.001868 cos γ − 0.032077 sin γ − 0.014615 cos 2γ − 0.040849 sin 2γ) minutes δ = 0.006918 − 0.399912 cos γ + 0.070257 sin γ − 0.006758 cos 2γ + 0.000907 sin 2γ − 0.002697 cos 3γ + 0.00148 sin 3γ declination offset = E_t + 4·longitude − 60·timezone minutes H = true solar time / 4 − 180 hour angle, 0 at solar noon cos Z = sin φ sin δ + cos φ cos δ cos H azimuth = atan2(sin H, cos H sin φ − tan δ cos φ) + 180

The atan2 form is used because it is unambiguous in all four quadrants; the result comes out measured from south and is shifted by 180° to read clockwise from north. The fractional year uses a fixed 365-day denominator even in a leap year.

Refraction is then added to the geometric altitude, in arc-seconds, divided by 3600:

elevation > 85° 0 5° < elevation ≤ 85° 58.1/tan e − 0.07/tan³ e + 0.000086/tan⁵ e −0.575° < elevation ≤ 5° 1735 + e(−518.2 + e(103.4 + e(−12.79 + 0.711 e))) elevation ≤ −0.575° −20.772 / tan e

Sunrise and sunset use the standard 90.833° zenith, which allows for refraction and for the finite diameter of the solar disc — which is why a computed equinox day is about 12.1 hours long, not 12.0. That calculation deliberately takes its declination from an unrefracted call, so refraction is not counted twice. Polar day and polar night return nulls and a flag rather than a nonsensical time.

One timing convention matters for any figure read off a sun path. An EPW record describes the interval ending at the stated hour, so hour index h spans h:00 to h+1:00 and the app evaluates the sun at its midpoint, h + 0.5. The hourly sun positions, the cursor marker, the shadow and the shadow trace all carry that half-hour offset. The drawn day arcs and analemmas do not — they are computed on the whole hour. So the plotted data points sit half an hour after the hour lines they are read against. At mid-latitudes that is a few degrees of azimuth, and it is a real offset, not a rendering artefact.

The degree-day convention is worth naming precisely because several exist and they do not agree. This is not the mean-daily-temperature method used by most published degree-day series. It accumulates a degree-hour for every hour and divides the total by 24, which the source justifies as handling partial days and gaps correctly — and which it does. It will not reproduce a published degree-day figure for the same station computed the daily-mean way, and the difference is largest in climates that cross the base temperature within a day. The code names no source for this convention.

Wind-rose binning

Frequency of each direction-sector and speed-band pair. Sector 0 is centred on north, so the raw bearing is shifted by half a sector before binning. Calm hours are separated rather than assigned a direction, and the source says why:

"Calm hours (speed below calmThreshold) are counted separately rather than assigned to a direction, because EPW records calm hours with direction 0, which would otherwise pile a spurious spike onto due north." This is a real and common defect in wind roses drawn without that precaution, and it is worth checking for in any rose you are shown: a suspiciously strong due-north petal in a climate with no northerly wind is usually this.

 An hour with a finite speed but a missing direction is counted in the total and then dropped, so the petals and the calm disc together can account for slightly less than the whole selection.

Missing values, and the "≥" rule

EPW writes a sentinel where a value is absent, and writers are not consistent about which sentinel they use. The parser therefore treats the documented value as a threshold rather than as an exact match. The source states it directly:

"Values at or above the sentinel are normalised to NaN by the parser (EPW writers are inconsistent, e.g. illuminance uses both 999999 and 999900), so the threshold is treated as '≥'."

Two details of that test matter. It compares the magnitude of the value, so −99.9 is discarded as missing exactly as +99.9 is. And the threshold sits an epsilon below the sentinel, so the sentinel itself reliably trips the test rather than surviving a floating-point comparison. A value becomes NaN in four cases: the column is absent from a short record, the column is empty, the text does not parse as a finite number, or its magnitude reaches the threshold.

The honest consequence: a genuine reading at or beyond the sentinel magnitude is thrown away. For most fields that is unreachable — no ceiling is 99,999 m — but aerosol optical depth is discarded at 0.999, which is a physically attainable value, and total sky cover is discarded at 99 tenths. This is the intended trade and it is the right one, but it is a trade.

Values that parse cleanly but fall outside the documented valid range are handled the other way round: they are kept, counted, and reported as a warning rather than silently nulled, on the principle that a real data problem should be visible. A file carrying 110% relative humidity will say so and will plot it.

Two structural limits, for completeness. Sub-hourly files are effectively unsupported: the records-per-hour value is parsed, but the internal calendar has 24 slots per day, so with more than one record per hour the later record overwrites the earlier. And EPW numbers its hours 1–24, where 24 is the interval ending at midnight of the same day; the parser maps that to a 0–23 index on that same day.

b. What the app ships with

No weather data at all. The app opens empty, on a card offering two public archives to download from, and every figure a student produces comes from a file they supplied.

This is a decision, not an omission, and the mechanism to reverse it is still in place. The build can gzip an EPW, base64-encode it, and substitute it into a constant that the app inflates at startup with the browser's own decompression — no library and no network request. That constant is deliberately empty. The source records why:

"The app ships with NO weather data: publishing it means redistributing whatever is embedded here to every visitor, and third-party weather files carry their own attribution terms. Students load their own EPW instead."

With the constant empty, the availability check is permanently false, the loader returns nothing, and the app goes straight to its empty state — which is the shipped behaviour, confirmed in the built file. The build prints a warning on every run to say no sample was embedded, so the state is deliberate and visible rather than forgotten.

What a mode actually does

Five modes — Thermal, Solar, Wind, Daylight and Comfort. Each carries a blurb, a list of views, a list of variables and a list of relevant controls. Switching mode has exactly four effects:

  1. It filters the view shelf to that mode's views, in that mode's order. A view you reached from elsewhere is appended rather than hidden, so nothing becomes unreachable.
  2. It chooses the opening view and variable. The current view is kept if it happens to belong to the new mode, otherwise the mode's first view is selected. The variable becomes the first of the mode's variables that the loaded file actually contains.
  3. It re-orders the variable menu into two groups — the mode's variables first, then everything else in the file.
  4. It gates two chart overlays: the degree-day overlay appears in Thermal mode, and the comfort band in Thermal and Comfort.

That is the whole of it. No statistical, psychrometric or solar function ever receives the mode or anything derived from it. Switching mode can change which variable is selected, which changes which numbers are on screen — but it changes the input, never the arithmetic. The same file, period and variable give the same numbers in any mode.

Two loose ends in the mode definitions, worth knowing if you read the source. The list of "relevant controls" each mode carries is almost entirely decorative: it is consulted once, to dim the date-and-time group, and it hides nothing. Every name remaining in those lists refers to a control that exists; three that did not — speedBands, comfortBand and adaptive — have been removed from them.

Compare

Compare splits the stage into two panels, A and B, from one of two sources: another period of the same file, or another file entirely. Every one of the twelve views renders into both panels; none opts out.

What is shared and what is not is the thing to get right before quoting a comparison. Only two things differ between the panels: the analysis period, in period mode, and the dataset, in file mode. Variable, units, theme, every statistical option, the massing parameters and the cursor instant are global and apply to both.

Colour scales are computed per panel, from that panel's own data. In period compare both panels draw on the same file, so the scales are genuinely identical and the colours are comparable. In two-file compare they are not: each panel takes its own minimum and maximum, so the same colour means a different value on the left and on the right. Read the numbers, not the colours, whenever the two panels hold two different climates.

Three further asymmetries: the readout tiles above the stage always describe panel A, never B; PNG and CSV export likewise always take panel A; and selecting the two-file source before loading a second file silently shows the first file in both panels with no warning.

Not modelled

These are the assumptions a student is most likely to make wrongly, because an environmental analysis tool would generally handle them.

Out
Any building
No fabric, no U-value, no thermal mass, no glazing, no orientation of a surface, no zone, no occupancy, no internal gain, no system and no control. The massing block casts a shadow and has no other property; it is a solid with dimensions, not a building.
Out
The other four comfort variables
Radiant temperature, air speed, clothing and metabolic rate enter nothing. The comfort evaluation is a rectangle on the psychrometric plane, fixed at still air; the clo values survive only as text in the two zone labels. No PMV, no PPD, no SET.
Out
Adaptive comfort
Implemented, tested, exported and never called. No control reaches it. Stated here as a limit of the shipped tool rather than of the code.
Out
Any energy calculation
No load, no demand, no consumption, no plant, no efficiency, no carbon. Degree days are a climate statistic here, not an energy estimate, and multiplying them by anything to get a load is your assumption, not the tool's.
Out
Solar radiation on anything but the horizontal
The file's global, direct and diffuse values are read and plotted as recorded. Nothing is transposed onto a tilted or vertical surface, so there is no irradiation on a façade, no incident-angle calculation and no shading factor.
Out
Climate change, trend or projection
A typical meteorological year is a synthesised representative year assembled from months of different real years. No date in it is a date that happened. There is no trend to extract, no future weather file generation, no morphing, and the year label on a record means nothing on its own.
Out
Design conditions
The DESIGN CONDITIONS header, which carries the percentile design temperatures an engineer sizes plant against, is in every EPW file and is never read. You cannot get a design condition out of this tool.
Out
Daylight saving and local clock time
Everything is local standard time. The HOLIDAYS/DAYLIGHT SAVINGS header is not read. An occupied-hours analysis over a summer period is therefore an hour out from the clock the occupants actually keep.
Note
Ground temperatures
Parsed from the header and available, but no ground-coupling calculation of any kind uses them.

What it is safe to cite this tool for

Cite it as an instrument for reading a weather file: the climate's structure through the year, its psychrometric shape, its solar geometry, its wind regime, and which passive strategies its outdoor conditions sit near. Do not cite it for a building's performance, for a comfort result about occupants, for an energy or carbon figure, or for anything that must satisfy a regulation. It computes properties of a climate, and a climate is not a building.

05

How exact the numbers are

Because these quantities are defined by published standards, "accuracy" splits into three separate questions that are easy to run together and should not be. How faithfully does the code implement the method it names? How much precision survives the arithmetic? And how representative is the file it was given? The three have different answers, and the third dominates.

Fidelity to the standard

Where the source cites an equation number, it implements that equation with its published coefficients, and the implementation is checked against published values — saturation pressure against ASHRAE Fundamentals Table 1 across −10 to 40 °C to within 0.05% — that table is named by the test suite, not by the application, and the 25 °C / 50% RH state against published psychrometric values. The departures are these, all of them deliberate or structural rather than errors:

Numerical precision

Every hourly series — read or derived — is stored in a 32-bit float. There is no 64-bit array anywhere in the application. The arithmetic itself runs at full double precision and the narrowing happens only at the store, so roughly seven significant decimal digits survive per value.

For weather data this is the right trade and costs nothing that matters: a dry bulb of 17.3 °C, an illuminance of 42,500 lux and a pressure of 101,325 Pa are all exactly or near-exactly representable, and the measurements themselves carry two or three significant figures. Worth knowing rather than worrying about. One reassurance: the missing-value test is applied before the narrowing, so no sentinel can slip through because of it.

The input, which is where the real uncertainty lives

A typical meteorological year is one synthesised year for one station. Its months are drawn from different real years, chosen to be individually representative, and stitched together. It therefore has no interannual variability in it, it contains no real extreme event in its real sequence, and it describes the station, not your site. A rooftop three kilometres away and forty metres higher, inside an urban heat island, is a different climate. Every figure this tool produces is exact about that file and inherits all of the file's distance from the place you are designing for. That distance is larger than every numerical consideration above, combined.

What is actually asserted

The parts of the arithmetic that can be checked, are, in an automated suite of 53 tests making 229 assertions across four files, run against three real weather files — Chicago O'Hare TMY3, London Gatwick IWEC and London St James's Park TMYx.

Units, and the difference between a temperature and a temperature difference

The SI / IP toggle converts every field by its own factor. Temperature is the one case where the conversion depends on what the number means: 20 °C is 68 °F, but a spread of 20 °C is a spread of 36 °F, not 68. The code keeps two separate converters for exactly this, and applies the difference form to the spread figure under the range tile.

Two gaps to know about. The difference converter is used in exactly one place, so any other interval-valued figure on screen — including the label under a comfort slider — goes through the absolute form. And degree-day totals are not converted at all, staying in °C·day whatever the toggle says.

Controls that change nothing numerical

Theme, presentation mode, PNG resolution, the analysis mode itself, the sun-path projection and its tint, the sunrise–sunset overlay, the shadow trace and analemma switches, and all camera movement in the 3D views. None of these touches a calculation. PNG resolution is worth one note: the chart is genuinely re-rendered at the higher density rather than a finished image being stretched, so the layout is identical and only the pixel count rises.

Massing rotation is not in that list. It is a model parameter, not a camera. Rotating the block rotates every vertex and every footprint corner before the shadow is projected, so the shape, extent and orientation of the computed shadow all change with it. Orbiting the camera changes nothing; rotating the block changes the result.

07

Compared with Climate Consultant and Ladybug

Where it should agree

  • The psychrometric quantities. Humidity ratio, enthalpy and wet bulb follow the ASHRAE Handbook formulations that all three tools use, at the same station pressure. A state computed here and in Climate Consultant should agree to the precision either displays.
  • The strategy polygons, in principle. The source names the Givoni–Milne construction "used by Ladybug and Climate Consultant" as the thing it follows, so agreement on the three strategies it draws is the expectation rather than a coincidence.
  • Solar position. The NOAA algorithm is the one most of this family of tools uses. Altitude and azimuth should agree to a fraction of a degree.
  • Descriptive statistics. A mean or a percentile over the same hours of the same file is the same arithmetic everywhere, subject to the percentile convention, which is the common linear-interpolation one here.

Where it will diverge

  • Strategy coverage. Three polygons here against the fuller set elsewhere. A climate whose hours fall in passive solar heating or dehumidification will show those hours as served by nothing, when another tool would name a strategy.
  • The comfort zone itself. The limits here are fixed at 19.5–24.5 and 22.5–27.5 °C. Tools that let you set clo, metabolic rate and air speed will compute a different zone for the same climate, because they are solving a comfort model and this is drawing a rectangle.
  • Adaptive comfort. Ladybug will give you an adaptive result. This will not.
  • The evaporative polygon. Built here from a 21 °C constant-wet-bulb line swept to 45 °C. A tool using a different wet-bulb limit will report a different percentage for an identical climate.
  • Counting on unclipped polygons. Where another implementation clips the polygon to saturation before counting, its percentage will be the smaller of the two.
  • Wind-rose percentages. Different sector counts and different speed bands make two roses of the same file numerically incomparable, as the opening notice says.
  • Degree days. The hourly-then-÷24 convention here will not reproduce a daily-mean degree-day series, and the gap widens in climates that cross the base within a single day.

The boundary that matters most: this tool does no energy modelling and is not a route to a compliance result. Ladybug is a front end to EnergyPlus and Radiance and can carry a climate into a simulation; Climate Consultant stops at climate analysis, as this does. Nothing here produces a load, a demand, an illuminance on a work plane or a figure that any regulation recognises. Use it to understand a climate and to decide what to simulate — then simulate it somewhere else.

08

Three exercises

Each isolates one idea and holds everything else fixed. The app ships with no weather data, so begin by downloading one: climate.onebuilding.org and energyplus.net/weather both publish free EPW files by station. Record the station name and the source for every file you use — you will need both to write up anything you find.

Exercise 01

A heating season is a shape, and a monthly mean hides it

  1. Load a temperate-climate file. Thermal mode, Annual heatmap, variable Dry bulb temperature, period 1 Jan – 31 Dec.
  2. Read the picture before any number. Where does the cold block sit, and at which hours of the day does it reach furthest into the year? Write down the two dates where the cold reaches the middle of the day.
  3. Switch to Monthly statistics. Write down the mean for the coldest month, and then the 5th and 95th percentile whiskers for that same month.
  4. Back to the heatmap. Set the degree-day base to 18, then 15.5, then 12, and watch the colour boundary move each time.
  5. Read the heating degree-day tile at each of those three bases and write all three down, with their bases.

Principle. A monthly mean is one number standing for about 720 hours, and it averages away exactly what a designer needs: how cold, for how long, and at what time of day. The whiskers begin to restore that; the heatmap restores it completely, because the eye reads a two-dimensional field faster than any table. Degree days are the third way of asking, and they re-weight by how far below the base an hour sat, not merely how often. The base is your assumption about the building, not a property of the climate — which the tool makes visible by re-colouring the heatmap when you change it. A degree-day figure quoted without its base is unusable.

Exercise 02

A climate rewards one passive strategy and refuses another

  1. Comfort mode, Psychrometric chart, passive strategies on, period 1 Jan – 31 Dec.
  2. Look at where the cloud of hours sits relative to the two comfort rectangles — left of them, inside, above, or to the right. Do this before reading any percentage.
  3. Write down the percentage against each of the three strategies in the legend. Note that they overlap, and that they do not sum to 100.
  4. Change the period to 1 Jun – 31 Aug and re-read all three. Then to the occupied preset, 08–18, and re-read again.
  5. Read the Comfortable hours tile, then the Outside comfort band tile. Write down both, and write one sentence on why they disagree.

Principle. The position of the cloud decides the strategy before any arithmetic does. A cloud sitting to the left of comfort is a heating climate, and no amount of ventilation moves it rightwards. A cloud sitting high and to the right is warm and humid, where evaporative cooling has nothing to work with and ventilation does what work there is. The same climate recommends a different strategy over summer than over the year, and a different one again over occupied hours — which is why a strategy claim that does not carry its period is not a claim about anything. The two comfort tiles disagree because they are two different quantities: one is a region of the psychrometric plane, the other is a dry-bulb band with humidity ignored.

Exercise 03

Latitude fixes the sun and almost nothing else

  1. Download two files at nearly the same latitude but in different situations — one maritime and western-coastal, one deep inland and continental. Aim for within two degrees of latitude.
  2. Load the first. Solar mode, Sun path dome. Note the solstice arcs and the day length.
  3. Load the second into the same view and satisfy yourself that the sun path is almost identical. That is the control in this experiment.
  4. Turn on Compare, set the source to Two files, and load the second file into panel B. Go to Annual heatmap, then Distribution, then Monthly statistics.
  5. Record for both: annual mean, annual minimum and maximum, and the difference between the warmest and coldest monthly mean. Then read both psychrometric charts.

Principle. Two sites at the same latitude receive the same sun on the same days, and can still differ by twenty kelvin in annual range. Ocean, altitude, prevailing wind and distance from a coast do the rest, and they do far more of it than latitude. This is the exercise that stops "what latitude is it?" being the first question asked about a site. One caution specific to this tool: in two-file compare the colour scales are computed separately for each panel, so the same colour means a different temperature on the left and on the right. Read the numbers, not the colours.

A caution for all three: quote the settings with the figure. Every number these exercises produce depends on a file you chose, a period you set and, for the comfort figures, on band limits and a humidity limit. A percentage without them cannot be checked by anyone reading you.

Everything on this page was read from the tool's source code at version 1.0.0, released 15 September 2026. Where a figure is quoted it is read, not estimated. Where the code names no source, or contains something the interface cannot reach, this page says so rather than passing over it.

For anything that must stand up, use a simulation tool and a measured or morphed weather file appropriate to the site. This tool is built to make a climate legible, and it contains no building model at all — deliberately, so that what it does do stays honest.
